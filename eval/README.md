# Mizan baseline benchmark

Small on purpose. Enough to tell whether a change helped, not a framework.

```bash
python -m eval.run_eval                  # all three sections
python -m eval.run_eval --only retrieval # ~2 min, no LLM calls
python -m eval.run_eval --only risk      # 40 LLM calls, ~15 min
python -m eval.run_eval --only ocr       # ~1 min
```

Results are written to `eval/results/baseline_<timestamp>.json` so two runs
can be diffed.

---

## What is measured

### 1. Retrieval — `Recall@3`, `Recall@10`, `MRR`

40 hand-labelled clauses in `data/clauses_gold.jsonl`, each with the Egyptian
Civil Code article that governs it. 20 rental, 8 sale, 6 employment, 6 general
contract law.

**The score is reported twice**, and the split is the point of the whole
section: once over all clauses, and once over only those whose gold article
actually exists in the corpus. A single Recall@K cannot tell "the retriever
could not find it" from "we never had it", and those two failures need
completely different fixes. At the time of writing corpus coverage is 100%, so
the two numbers coincide — which is itself the finding: retrieval misses are
retrieval's fault, not the corpus's.

Gold labels were verified against the corpus: every one of the 31 distinct
article numbers exists, and its indexed text matches the topic it was labelled
for.

### 2. Risk detection — `Precision`, `Recall`, `F1`

Positive class is "high risk" (أحمر). Same 40 clauses, hand-labelled red /
not-red. Precision is the trust number — how often a red flag was deserved.
Recall is the safety number — how many real problems were missed.

`evidence_mix` is reported alongside: how many verdicts came back grounded,
from model knowledge, or with insufficient support. A high F1 built on
ungrounded verdicts is not the same result as the same F1 built on grounded
ones.

### 3. OCR — `CER`, `WER`

Three pages in `data/ocr/`, each a `_raw.txt` (damaged) and `_ref.txt`
(reference), scored at three stages: raw, after deterministic repair, after
LLM reconstruction.

- **page1** is real: raw Tesseract output from a user's scanned contract,
  paired with a hand transcription. The reference is a careful reading, not a
  verified transcription — treat its absolute CER as indicative.
- **page2, page3** are generated by `make_ocr_pages.py` from contract text, so
  their reference is exact. The damage applied is the distribution measured on
  page 1: kashida runs read as dals, the observed letter-confusion table,
  glued digits, broken lines. Fixed seed, so the benchmark does not drift.

**What this does not measure:** the OCR engine itself. That needs a Tesseract
binary and real page images. What is scored here is the repair stage — which
is the stage this project actually changes. When Tesseract is installed,
`engine_measured` in the results turns true; wiring the engine into the
comparison is a small addition on top of what is here.

## Adding to the benchmark

Append to `data/clauses_gold.jsonl`:

```json
{"id": 41, "contract_type": "residential", "risk": "red",
 "gold_articles": ["571"], "gold_law": "القانون المدني",
 "clause_text": "...", "note": "why this article governs it"}
```

`contract_type` must be one of the nine ids the retriever accepts. Verify a new
gold article exists and is on-topic before trusting a score that uses it.
